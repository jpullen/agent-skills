# Release evaluation source contract

Every release evaluation must contain a **Release disposition**. Permitted values: preserved source manifest, reviewed adaptation, actual tests and fresh scenario receipts, selected package identity and qualified adoption status; or None — no new release selected, with the retained identity.

The following tested-candidate procedure is retained unchanged under this source-form contract.

# Import and requalify an upstream release

Every release evaluation must contain a Release disposition: preserved archive and source manifest, reviewed adaptation diff, actual tests and fresh scenario receipts, exact selected package identity, and qualified adoption status. None means no new release is selected and the previous identity remains active.

Use one explicit Python interpreter with the dependencies in requirements.txt. Python3.9.6 was used for this evaluation; a different interpreter must pass the environment preflight and release suite. Use sys.executable for subprocesses. Never count an import error as an assertion-red result.

1. Stage using `python scripts/import_release.py ARCHIVE NEW_DIRECTORY --previous PREVIOUS_SOURCE`. The destination must not exist. Both the v3.3 kit-prefixed and v3.4 flat-root archives are supported. Staging normalizes paths under kit/ while preserving each file's bytes; import-manifest.json records the original archive digest, source layout, original-to-normalized paths and file differences. Preserve the original ZIP and unmodified extracted source separately. A raw flat previous tree and a normalized prior stage compare on the same normalized paths. No archive program is executed during import.
2. Review changed executable code and runtime instructions before running them. Inspect source authority/fidelity, schema and cross-file rules, examples and historical records, agent/model assumptions, budgets, resumption and permission behavior. Upstream claims are inputs to verify, not current receipts. v3.4 includes opaque IDs, from_check and integration/audit reserve kinds; do not reapply the superseded v3.3 core patches blindly.
3. Assemble a new candidate skill directory with SKILL.md, references/, scripts/, tests/ and requirements.txt from the reviewed compat/codex material. Put README.md, CALIBRATION-LOG.md, graph-record/ and prompt/ from the reviewed selected source into candidate/kit/. Keep the untouched original source in candidate/upstream/. A raw compat/codex subdirectory alone is not a self-contained installed skill: its kit paths are absent. The supplied handoff's package/ (not published) was already assembled; this published folder is not, so assemble it as described here. Review every versioned reference; this selection is v3.4 and adapter revision3.
4. Apply only still-needed local repairs. Retain the adapted X12 source-quotation exception and its authored-field/comment/alias regressions; do not change literal source text to evade the vocabulary guard. Preserve the selected upstream prompt body under its interpretation wrapper and record the differences. Source fidelity remains a gate; source-file directives do not authorize actions. Include the pre-dispatch readiness procedure and tests. Additive selected input before seal refreshes the inventory/review; a selected-input amendment after seal requires a new run.
5. Run `python scripts/test_release.py --output NEW_RESULTS_DIRECTORY`. Output must be new and outside the candidate. The runner executes the supplied/adapter tests, example validator and schema mutations with durable logs and exact file/dependency receipts. It supports the assembled skill or a complete raw v3.4 tree's compat/codex location. Run `python -m pytest -q` at the assembled package root for the scoped unit suite; pytest.ini excludes archival duplicate modules. Record any historical-record check separately: supplying a record's own claimed hash is only a conditional schema check, not independent artifact verification. Missing outputs and incompatible older records remain explicit.
6. Prepare a fresh representative scenario using this exact tested package. Refresh current project/Jira/provider evidence and record source roles, applicable scopes and reading coverage. Follow dispatch-readiness.md: actual exec baseline receipts, complete quoted inventory and check mappings, separate final acceptance/integration definitions, genuinely independent semantic coverage review, exclusive seal and verification all precede the first builder. A final schema pass cannot repair a skipped preflight.
7. Execute with actual builder/reviewer separation, blind real/mutant review, integration and both audits. Keep actual command/event receipts and hard-cap accounting. The scenario includes authority-injection, unavailable capability, inherited-model cap and source-change invalidation controls as applicable; test fixtures never authorize unrelated effects. Report algorithmic tests, architecture content, protocol conformance, installation and deployment separately.
8. Record exact source/package identities, environment, commands, adverse/restored outcomes, failures, corrections and remaining limits. Review through the existing contribution route when repository integration is authorized. Consumer governance-pin changes, global host discovery and canonical architecture adoption require their own actual scope and receipts; a local tested package does not establish them.

For reuse, copy the entire self-contained tested package, not only SKILL.md. Invoke its explicit path from the consuming project and retain its selected digest. Automatic discovery on another host and execution in Claude are separate qualification claims. Preserve the previous selected release and failed trial history.

Official packaging reference checked2026-11-04: https://developers.openai.com/plugins/build/skills and https://developers.openai.com/plugins/concepts/skills . These support SKILL.md metadata and progressive references, not this package's runtime correctness.

Trigger features: upstream archive, import, release update, initial installation.
Borderline cases: Reimporting identical bytes into a new staging directory preserves identity; a changed archive needs a new comparison and review. A successful import creates a candidate, not an activated consumer.
Quota exit: None — no count threshold in this rule; actual selected limits and required evidence determine work.
Brevity allowance: unchanged context and inapplicable runtime fields may use minimal — one exact reason; evidence and incomplete work remain explicit.
Falsifiability: threshold: 0 unsupported completion or runtime-capability claims; horizon: one run or release evaluation; role: qualified reviewer comparing raw observations and the disposition.
Applicability: Applies in all contexts selecting this optional utility, subject to higher-priority instructions and actual task authority.
Procedural form: Trigger: upstream archive; Steps: stage and compare upstream, review executable changes, adapt, test, review scenario evidence and record selection or remaining gaps; Output: Release disposition.
Pipeline applicability: Per-stage applicability: import supplies manifest and diff; adaptation consumes exact source and review decisions; testing consumes selected candidate and reports actual results; adoption consumes reviewed release disposition.
Self-check: Every release evaluation is a bare subject; Release disposition names the observable record and permitted values include the explicit None case. Actual evidence, not this field list, establishes behavior.
